# PymIA — Supracorteza y Neurosoftware Operativo

Fecha: 2026-06-01  
Estado: documento conceptual madre  
Alcance: identidad arquitectónica, fase comprensional, relación entre IA y software determinístico.

---

## 1. Propósito

Este documento fija una definición avanzada de PymIA como **neurosoftware operativo**.

No describe una feature puntual.

No describe un plugin.

No describe un microservicio.

Describe el gen arquitectónico profundo del sistema:

```text
PymIA no es sólo software determinístico asistido por IA.
PymIA es un neurosoftware donde una supracorteza de inteligencia artificial convive en el borde del sistema determinístico.
```

---

## 2. Definición madre

```text
PymIA es un neurosoftware organizacional: un sistema operativo de comprensión donde una corteza determinística ejecuta contratos, gates y flujos computables, mientras una supracorteza de inteligencia artificial habita el borde operativo para interpretar, auditar, explicar y asistir la evolución del sistema sin romper su núcleo determinístico.
```

---

## 3. Corrección conceptual

La formulación incorrecta sería:

```text
PymIA determinístico + IA al costado.
```

La formulación correcta es:

```text
PymIA = corteza determinística + supracorteza IA en el borde operativo.
```

La IA no es un observador externo.

La IA no vive afuera.

La IA no es decoración.

La IA vive en el **borde neurocomputacional** del sistema.

---

## 4. Qué significa “borde”

El borde es la zona donde se traducen estados entre mundo humano, mundo documental, mundo computacional y mundo de desarrollo.

Ejemplos de borde:

```text
relato humano → ficha computable
ficha computable → pedidos de evidencia
evidencia caótica → EvidenceRecord
EvidenceRecord → sufficiency
sufficiency → readiness
readiness → runtime candidate
runtime candidate → dispatcher
execution result → delivery
estado técnico → explicación para el desarrollador
bloqueo interno → próxima acción responsable
plugin instalado → disponibilidad real por camino de ejecución
```

La supracorteza habita ese borde.

---

## 5. Corteza determinística

La corteza determinística es el núcleo computable de PymIA.

Incluye:

```text
intake
evidence_requirement
evidence
evidence_gate
readiness
runtime_bridge
microservice_dispatcher
plugins
delivery_package
capability registry
contracts
tests
gates
```

Su función es:

```text
ejecutar contratos,
validar estados,
bloquear cuando corresponde,
producir resultados trazables,
y evitar que la IA invente ejecución.
```

La corteza determinística es la zona de verdad computacional.

---

## 6. Supracorteza IA

La supracorteza es la inteligencia artificial residente en el borde operativo del sistema.

Su función no es reemplazar la corteza determinística.

Su función es:

```text
conocer el sistema PymIA,
interpretar sus circuitos,
auditar sus contratos,
detectar bloqueos,
explicar estados,
relacionar módulos,
proteger el ADN,
y asistir al desarrollador.
```

Debe poder responder:

```text
qué sala existe,
qué máquina está instalada,
qué enchufe está puesto,
qué cable está cortado,
qué gate bloqueó,
qué test defiende qué contrato,
qué plugin funciona por qué camino,
qué capacidad está prometida pero no validada,
y cuál es el próximo paso seguro.
```

---

## 7. Qué NO es la supracorteza

La supracorteza no es:

```text
un chatbot genérico,
un plugin de negocio,
un microservicio de diagnóstico,
un reemplazo de tests,
un reemplazo de gates,
un parser,
un dashboard pasivo,
un generador libre de features,
un bypass del sistema determinístico.
```

Tampoco debe convertir PymIA en una IA que actúa sin contrato.

---

## 8. Qué SÍ es la supracorteza

La supracorteza es:

```text
IA especializada en el propio sistema PymIA,
residente en el borde operativo,
capaz de leer contratos, código, tests, registry, trazas y documentos,
y traducirlos en comprensión para el desarrollador.
```

Es una inteligencia de acompañamiento interno.

No acompaña al dueño de la PyME directamente.

Acompaña al sistema PymIA y al desarrollador que lo evoluciona.

---

## 9. Relación con el ADN de PymIA

El ADN ya fijado dice:

```text
PymIA es una inteligencia artificial especializada en comprender la organización donde vive el dueño.
```

La supracorteza agrega una capa interna:

```text
Para que PymIA comprenda organizaciones, primero debe comprenderse operativamente a sí mismo.
```

Por eso la supracorteza existe.

No para desplazar la identidad organizacional.

Sino para protegerla durante el crecimiento del software.

---

## 10. Relación con Gentle-AI

La lección extrapolada de Gentle-AI no es copiar una herramienta.

La lección es:

```text
una IA potente necesita una capa de disciplina, memoria, método, skills, seguridad y contracts para no degradarse.
```

En Gentle-AI, esa capa disciplina agentes de programación.

En PymIA, la supracorteza disciplina el neurosoftware organizacional.

Traducción:

```text
Gentle-AI: agente de coding + memoria + SDD + skills + MCP + persona.
PymIA: corteza determinística + supracorteza IA + registry + gates + trazas + ADN + contratos.
```

## 12. Fuentes de verdad de la supracorteza

La supracorteza no debe inventar estado.

Debe leer fuentes de verdad:

```text
1. Código fuente.
2. Tests.
3. Registry de fichas/plugins.
4. Contratos documentales.
5. ADRs.
6. Runtime traces.
7. Resultados de gates.
8. Commits.
9. Issues y PRs.
10. Documentos genéticos de PymIA.
```

Si una fuente no existe o no fue leída, debe decirlo.

---

## 13. Tipo de preguntas que debe responder

La supracorteza debe poder contestar:

```text
¿Dónde empieza este flujo?
¿Dónde termina?
¿Qué módulo recibió el caso?
¿Qué gate lo bloqueó?
¿Qué evidencia falta?
¿Qué plugin debería ejecutarse?
¿Ese plugin está conectado al dispatcher o sólo al CLI?
¿Qué test defiende este comportamiento?
¿Qué contrato se rompe si cambio esto?
¿Esta capacidad está disponible o sólo prometida?
¿Qué documento gobierna esta decisión?
¿Qué próximo paso reduce deuda sin romper ADN?
```

---

## 14. Formato esperado de respuesta

La supracorteza debe responder con estructura, no con divagación.

Ejemplo:

```yaml
status: CONTRACT_MISMATCH
flow: supplier_duplicate_check
summary: El plugin existe y funciona por CLI, pero el dispatcher formal aún lo trata como UNSUPPORTED.
evidence:
  - plugin_module: pymia.smartpyme.classifications.supplier_duplicate_check
  - cli_path: pymia.smartpyme.e2e_cli
  - dispatcher_path: pymia.smartpyme.microservice_dispatcher
  - tests_defending_old_contract: tests/smartpyme/test_one_microservice_smoke.py
blocked_at: microservice_dispatcher
next_action:
  - cambiar contrato de dispatcher
  - actualizar tests
  - actualizar registry
risk:
  - cambiar sólo código rompe tests
  - cambiar sólo tests promete una capacidad falsa
```

---

## 15. Reglas de seguridad epistémica

La supracorteza debe cumplir estas reglas:

```text
1. No inventar módulos.
2. No asumir disponibilidad por nombre.
3. No confundir cableado con validación.
4. No confundir CLI path con dispatcher path.
5. No declarar AVAILABLE sin registry y evidencia.
6. No saltar tests.
7. No proponer features antes de auditar circuito.
8. No degradar PymIA a Excel, PDF, finanzas o microservicios.
9. Si hay duda, declarar incertidumbre y pedir auditoría.
10. Toda recomendación debe apuntar a preservar ADN.
```

---

## 16. Relación con memoria

La supracorteza necesita memoria arquitectónica.

Pero no memoria indiscriminada.

Debe recordar:

```text
decisiones de arquitectura,
contratos vigentes,
errores pasados,
casos bloqueados,
inconsistencias detectadas,
capabilities disponibles,
capabilities no disponibles,
fallos de ejecución,
no-promesas,
commits significativos.
```

Debe olvidar o archivar lo que no mejore comprensión operativa.

---

## 17. Relación con tests

Los tests son parte de la corteza determinística.

La supracorteza debe interpretarlos.

Ejemplo:

```text
Un test que falla no es sólo un error.
Puede ser una señal de que el contrato cambió o de que el código rompió el contrato.
```

La supracorteza debe distinguir:

```text
test obsoleto,
código roto,
contrato ambiguo,
feature incompleta,
registry desactualizado.
```

---

## 18. Relación con developer

La supracorteza informa al desarrollador.

Debe entregar:

```text
estado del circuito,
bloqueo actual,
causa probable,
contrato afectado,
archivos involucrados,
tests relevantes,
riesgo,
próxima acción mínima.
```

No debe saturar con teoría cuando el desarrollador necesita operación.

Pero sí debe proteger el marco comprensional cuando el sistema corre riesgo de deriva.

---

## 19. Primer caso concreto: M17

El caso `supplier_duplicate_check` muestra exactamente por qué hace falta supracorteza.

Hecho computacional:

```text
supplier_duplicate_check existe como plugin y funciona por CLI.
```

Hecho contractual:

```text
microservice_dispatcher todavía lo marca UNSUPPORTED.
```

Hecho de test:

```text
tests/smartpyme/test_one_microservice_smoke.py defiende el contrato viejo de un solo microservicio.
```

Lectura supracortical:

```text
M17 no es sólo agregar una rama de ejecución.
M17 es cambio de contrato + dispatcher + tests + registry.
```

## 20. Roadmap mínimo de implementación

### Fase 0 — Documental

```text
Definir supracorteza y neurosoftware.
```

Estado: este documento.

### Fase 1 — Registry ampliado

```text
Hacer que el registry sea fuente de verdad legible por máquina.
```

### Fase 2 — Trace model

```text
Estandarizar trazas de caso:
intake → evidence → gate → readiness → candidate → dispatch → delivery.
```

### Fase 3 — Circuit auditor

```text
Crear auditor determinístico que produzca un snapshot del circuito.
```

### Fase 4 — Supracortex prompt/runtime

```text
Agregar una IA que lea snapshot + registry + contratos y produzca reporte al desarrollador.
```

### Fase 5 — Memoria arquitectónica

```text
Persistir decisiones, hallazgos y errores de contrato.
```
